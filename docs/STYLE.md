# Стиль коду Toon Warfare

Коротко: як тут пишуть код, щоб новий файл читався так само, як старі. Інструменти
(`rustfmt.toml`, `clippy.toml`, `[workspace.lints]` у `Cargo.toml`) перевіряють частину
цього автоматично; решта — домовленість.

## Перед комітом

```sh
cargo fmt
cargo build --release
cargo clippy --workspace --all-targets   # без нових попереджень
cargo test --release
```

Один логічний крок — один коміт. Повідомлення англійською: заголовок до ~70 знаків у
наказовому способі («Pick the nearest body without panicking on NaN»), далі — що було не так
і чому зроблено саме так.

## Форматування й лінти

* `rustfmt` зі стабільними налаштуваннями з `rustfmt.toml` (ширина 100). Нічних опцій немає.
* Лінти спільні для всіх крейтів (`[workspace.lints]`). Новий `allow` — лише з коментарем,
  чому лінт тут не підходить; точковий `#[allow(...)]` — над тим самим рядком, теж із
  поясненням.
* `unsafe` заборонено (`deny`). Єдиний виняток — `mesh::quad_gl()` у клієнті (доступ до
  GL-контексту macroquad); новий `unsafe` іде лише через такий самий маленький
  задокументований хелпер із коментарем `// SAFETY:`.
* `vendor/macroquad` — чужий код із нашим патчем; стиль і лінти на нього не поширюються,
  міняти його лише в крайньому разі й з описом у `Cargo.toml`.

## Іменування

* Типи `CamelCase`, функції й змінні `snake_case`, константи `UPPER_SNAKE_CASE` — як
  звичайно в Rust.
* Назва каже, *що це в грі*, а не як влаштовано: `lying_near`, `hold_range`,
  `sight_fits`, а не `get_items2` чи `calc`.
* Методи `Game` на сервері, що стосуються одного режиму чи системи, мають її префікс:
  `br_jump`, `sab_plant`, `car_enter`, `box_take`.
* Булеві — питанням або станом: `alive`, `in_plane`, `can_spawn()`, `is_bot()`.
* Одиниці — у назві або в doc-коментарі: метри, секунди, м/с, радіани
  (`DOOR_REACH: f32 = 2.8; // m from the eyes`). Час сервера — `f64` секунд, тривалості —
  `f32`.

## Де живуть числа

* `shared/consts.rs` — числа, які мають збігатися на клієнті й сервері (радіуси, тривалості,
  швидкості, ліміти протоколу).
* `shared/tuning.rs` — те, що адміністратор сервера може змінити (`Tuning` іде клієнтам при
  підключенні): рух, зброя, гранати, серії.
* `server/config.rs` (`server.json`) — налаштування сервера, не гри: порти, ротація, боти,
  таймінги матчу.
* Константа, потрібна одному модулю, — `const` на початку цього модуля з doc-коментарем.
* Число просто в коді — лише очевидне (0, 1, 0.5 для половини, π) або з коментарем поруч,
  що воно означає.

## Порядок у модулі

1. `//!` — що це за модуль і за що він відповідає (одним-двома реченнями).
2. `use` (rustfmt їх сортує).
3. Константи.
4. Типи (`struct`, `enum`) з їхніми `impl`.
5. Вільні функції.
6. `#[cfg(test)] mod tests` наприкінці.

Великий `impl Game` на сервері розкладено по файлах за системою (`br.rs`, `sab.rs`,
`doors.rs`, `cars.rs`…): нова система — новий файл із власним `impl Game`.

## Помилки

* **Дані ззовні** (мережа, файли, `server.json`, адмінка) ніколи не валять процес:
  `Option`/`Result`, `let … else { return }`, `get()` замість індексу. У модулях, що читають
  датаграми (`shared/net.rs`, `server/netserver.rs`), `clippy::unwrap_used` попереджає.
* Числа від клієнта перевіряються на `is_finite()` до будь-якого використання; порівняння
  `f32`/`f64` для сортування й пошуку найближчого — `total_cmp`, не
  `partial_cmp().unwrap()`.
* `expect("…")` — лише для інваріанту, який код сам гарантує, і рядок пояснює чому
  («just inserted», «at least one spawn per team»). `unwrap()` у грі — лише там же, де
  поруч видно, чому він не впаде.
* У тестах `unwrap` дозволено (`clippy.toml`).

## Логування

* Сервер: `println!("[підсистема] текст")`, підсистема в квадратних дужках (`[game]`,
  `[net]`, `[master]`, `[http]`). Текст для оператора сервера — українською, як і решта
  консолі. Події матчу — через `Game::logf` (вони ж ідуть у веб-адмінку).
* Клієнт: `eprintln!` лише для помилок, які гравець не побачить на екрані.
* Не логувати щотіку чи щокадру.

## Коментарі й тексти

* Коментарі в коді — **англійською**: пояснюють *чому* і що це означає в грі, а не
  переказують рядок. Doc-коментар (`///`) — на кожному публічному елементі.
* Усе, що бачить гравець, — через `lang.rs`: `t("укр", "eng")` або `tr!("укр {x}", "eng {x}", x)`.
  Жодних рядків для гравця в коді напряму.
* Документація для гравців і адміністраторів — двомовна: `docs/GUIDE.md` і
  `docs/GUIDE.en.md` міняються разом.

## Мережа й детермінізм

* Будь-яка зміна того, як повідомлення лягає на дріт (`shared/protocol.rs`, `shared/net.rs`)
  — це підвищення `PROTOCOL_VERSION` у `shared/consts.rs` у тому ж коміті та оновлені
  `fuzz`/`net_e2e`.
* Руйнація (`shared/destruct.rs`) і фізика (`shared/physics.rs`) мають давати однаковий
  результат на сервері й кожному клієнті: без випадковості без спільного зерна, без порядку
  ітерації `HashMap` у результатах, без залежності від часу кадру. Тест `wreck.rs` це
  перевіряє.
* Сервер авторитетний: клієнт може показувати відгук одразу, але рішення (влучання,
  підбір, двері) ухвалює сервер, і клієнт приймає його відповідь.

## Тести

* Логіка без рендеру — unit-тест у тому ж файлі (`mod tests`) або інтеграційний у
  `crates/*/tests/`. Назва тесту — речення про поведінку: `a_knife_ignores_a_body_with_a_broken_position`.
* Виправлена вада — тест, який падає на старому коді.
* Дуже довгі тести — `#[ignore]` з поясненням, як їх запустити (як `soak.rs`:
  `cargo test --release -- --ignored`).
